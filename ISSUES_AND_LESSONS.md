# Problems encountered and what they taught us

This is a public summary of the JEE project record. It distinguishes measured failures from possible explanations. Private exam-question images, model traces, review notes and user attempts stay outside this repository.

| Issue | What we observed | What we can conclude now |
|---|---|---|
| **Source and answer quality** | One archived answer key did not match the actual displayed expression. Other questions needed careful reading of diagrams, units, options, alternatives and physics/chemistry sign conventions. | A key match alone is not sufficient for a reliable training or evaluation example. Source crops and independent solutions need review before a problem is admitted. The mismatched item was reported separately instead of quietly rescoring the original test. |
| **Training examples were few and varied** | A question family can yield several exercises but remains one independent source problem. Early pilots had only a handful of families; later experiments used 30 or 60. | Hundreds of derived task views do not equal hundreds of independent problems. We group related versions to keep them on one side of train/evaluation splits. |
| **Validation gain failed to generalize** | The first controlled adapter scored 11/12 versus 9/12 unchanged on checkpoint-selection validation, then tied 22/29 on a separate evaluation. | Selection-set improvement is a lead to investigate, not evidence of a generally better JEE solver. [Timeline](EXPERIMENT_HISTORY.md) |
| **More updates could damage output** | In the first learning and Recipe02 studies, later checkpoints often gave very short, incomplete answers. | We need early stopping and output-quality checks. Lowering the learning rate removed that particular short-output mode in a later diagnostic, but did not establish broad answer gains. [Checkpoint chart](charts/training_trajectories.png) |
| **Correct answers can contain invalid working** | The 16-layer arm got 8/12 strict answers versus 7/12 unchanged on reused Validation01, while procedure points fell to 14/24 versus 17/24. | We must score method and calculation as well as the final answer. More adapted layers alone are not the current recipe. [Tradeoff chart](charts/latest_tradeoffs.png) |
| **Repetition and failure to stop** | Some traces reconsider a settled step until the token cap; a recent exploratory ionization question looped under the 16-layer adapter. | Increasing the output budget is not a demonstrated fix for a repeated invalid step. That single user attempt does not prove the adapter caused the loop; a matched unchanged-base replay would be needed. |
| **Graph and decomposition benefits remain unproved** | A forced decomposition prompt lost to direct answering on an initial 18-question pilot, and the later training did not isolate graph use as its only changed factor. | Concept/method links are useful structure for authoring and a future harness, but we cannot claim that a knowledge graph has improved 9B solving accuracy. |
| **Local and browser deployment are different experiments** | The local lab runs pinned MLX 9B with optional adapters and saves attempts. The static site uses unchanged 0.8B ONNX in WebGPU. A browser smoke gave a fluent but wrong simple calculation on one run. | A working browser demo is not proof that the trained 9B runs in browsers or that either model is scientifically reliable. The browser harness has a narrow independent check, not a general verifier. |
| **Adapter conversion and browser export are separate gates** | The MLX LoRA delta mapped exactly to PEFT and ran on upstream BF16 with matching prompts/tokens/top-one next tokens on synthetic text/image fixtures. Current public Optimum code does not register Qwen3.5 export, while Transformers.js has runtime support but no public Qwen3.5 conversion script. | The learned update is portable to standard PEFT, but no 9B Transformers.js model was produced. A community ONNX base cannot by itself deploy our trained weights. [Full result](research/EXPORT09B01_STAGE_B_RESULT.md) |
| **A second visual model has a real cost and error boundary** | A small VLM can normalize text/tables and report uncertainty, but transcription can erase geometry, arrows, stereochemistry or superscripts; two models also add download, memory and latency. | The first product build should use the solver's integrated vision. A small frontend remains a measured hybrid ablation, not the sole source of truth. [Ablation plan](research/VISION_FRONTEND_ABLATION.md) |
| **Operating and recovery limits** | A directly opened `file://` lab page could not reach a stopped local server. Training can be interrupted by a shutdown. | The local lab must run through its loopback server; training saves durable per-update recovery state. A local checkpoint is not an off-device backup. |

The current research decision is **no promoted adapted checkpoint**. The next learning question is whether better, shorter execution-and-repair targets and a common verification harness improve both reasoning and answer delivery on *new* independent questions. The protected 2026 final reservation has not been used to rescue an unsuccessful checkpoint.

The full [9B training retrospective](TRAINING_RETROSPECTIVE.md) separates measured contributors from unresolved hypotheses and records the safeguards for the approximately 4B track. The next model will be chosen through the published [staged 4B-class selection plan](research/MODEL_SELECTION_4B_PLAN.md).
